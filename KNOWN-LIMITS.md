# Known limits

Limits that are known and judged out of scope for the current stage, one per
line: where they are in the code, what they allow, why they are left and the
pull request that raised them.

- scripts/probe-default-tier-load.sh:955 — the top-level .claude folder and .claude.json files of the target home are exempt from load C's no-write check, so a hook could write there unseen — out of scope for alpha: documented in the README and the script header, and only the pinned ledger commit runs under it (harness-core#3 r1)
- scripts/probe-default-tier-load.sh:616 — the subagent reader trusts the order of events in Claude Code's own stream, so a result placed before its tool_use, or after the final result event, is not refused — out of scope for alpha: the probe trusts the stream the session wrote (harness-core#3 r3)
- scripts/probe-default-tier-load.sh:616 — a forged event that is fully consistent (the right tool-use id and the right parent) reads as a real one, so a hand-built stream could still give B2 PASS — out of scope for alpha: the probe trusts the stream the session wrote and does not sign it (harness-core#3 r3)
- scripts/probe-default-tier-load.sh:627 — a subagent that starts its own subagent is not followed: that depth-2 subagent's Bash carries its own Agent call's id, is not credited to the first Agent call, and so reads as no nested Bash call (UNVERIFIED) — out of scope for alpha: the probe asks for one general-purpose subagent with one Bash call (harness-core#3 r3)
- scripts/probe-default-tier-load.sh:651 — B2 accepts only the exact command its prompt hands the subagent, so an honest subagent that rewrites it (a wrapper, a prefix, a suffix) fails B2 closed: UNVERIFIED or FAIL, never a false PASS — out of scope for alpha: the prompt asks for the command verbatim, and a live sample ran exactly that command (harness-core#3 r4)
- .github/workflows/ci.yml:199 — the tag check (check-marketplace.py --source) attests only for an unmodified workflow and script: it runs on the pull_request event from the pull request's own checkout, so a pull request that edits ci.yml or the script can delete the step, drop --expect-owner, or set a proxy and CA store that answers for api.github.com, and ambient same-user state (the process environment, the CA store, PATH, the interpreter) is not checked — out of scope for alpha: workflow and script edits are part of the reviewed diff, and running the attestation from main's trusted code is a separate follow-up (replaces harness-core#4)
- plugins/rails/hooks/destructive-command-guard.sh:2970 — the worktree root still comes from git (`git rev-parse --show-toplevel`), so a repository-local `core.worktree` can move it; the guard clears injected git configuration, not the repository's own — out of scope for this row: repository configuration is the repository owner's, and the pins suite holds a row that depends on it (the rails plugin's first pull request)
- plugins/rails/hooks/destructive-command-guard.sh:2243 — the merged-or-pushed removal route is removed, so when the delegation loop arms its cleanup registry (checkpoint 4) a registered tree with ignored files other than Python caches is denied, where the source accepted it on merged-or-pushed evidence — out of scope until that route returns in the lane layer (the rails plugin's first pull request)
- plugins/rails/hooks/destructive-command-guard.sh:2290 — every git worktree remove of a tree that is not below a temp folder and that no registry or authorization accepts is a hard deny; the person runs the removal by hand, outside Claude Code — out of scope: the repository can forge merged-or-pushed evidence, so no such route is offered (the rails plugin's first pull request)
- plugins/rails/hooks/destructive-command-guard.sh:119 — `/usr/local/bin`, `/opt/homebrew/bin` and the Linuxbrew root (`/home` followed by `/linuxbrew/.linuxbrew/bin`) are trusted roots that the person's own account can write on a Homebrew or Linuxbrew machine, so a jq, wc, tr, git or grep planted there by that account is trusted — out of scope: a planted program there is the account's own; for lanes the sandbox's write envelope is the backstop (the rails plugin's first pull request)
- plugins/rails/hooks/destructive-command-guard.sh:1422 — a plain `rm FILE` with no option, and any relative rm target from a working folder in no git repository, are hard denies the person cannot approve through the permission prompt; with the home work-folder rule gone and no scratchpad passed, every explicit rm from such a folder denies — out of scope: the source's strictness is kept, and the checkpoint 2 walk judges it (the rails plugin's first pull request)
- plugins/rails/hooks/destructive-command-guard.sh:2940 — any inherited git repository selector (GIT_DIR, GIT_WORK_TREE and the other seven) denies every judged rm and worktree removal, even one the selector does not affect — out of scope: the command runs with the same environment, so the guard would otherwise judge a different repository from the one it changes (the rails plugin's first pull request)
- plugins/rails/hooks/destructive-command-guard.sh:1633 — on a system whose stat is the uutils rewrite of coreutils (newer Ubuntu releases ship it as `/usr/bin/stat`), stat prints a worktree's birth time in whole seconds where the guard needs nanoseconds, so every identity-checked worktree removal denies, failing closed; the person sees `Destructive command guard denied the command (reason=unsafe_worktree_remove): git worktree remove must name exactly one registered or authorized worktree and never --force; otherwise run the removal yourself, outside Claude Code.` and runs the removal by hand, outside the session — out of scope until uutils support lands: the guard has no fallback to whole seconds by design, and CI's pytest job runs on ubuntu-24.04, whose stat is GNU (the rails plugin's first pull request)
- plugins/rails/hooks/hooks.json:13 — `"onFailure": "block"` needs Claude Code 2.1.295 or later; on an older version a guard that times out, cannot start or exits other than 0 and 2 lets the command run — out of scope: the plugin's minimum Claude Code version (the rails plugin's first pull request)
- scripts/check-marketplace.py:525 — a self-hosted runner behind a proxy cannot pass the --source step: in CI the tripwire refuses any proxy or CA override (https_proxy, all_proxy, ssl_cert_file, ssl_cert_dir, in any letter case) before any request, and the refusal names the variable — out of scope for alpha: the default runner is GitHub-hosted and sets none of them (replaces harness-core#4)
